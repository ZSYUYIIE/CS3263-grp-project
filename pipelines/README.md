# Route A: direct LLM answers

Route A gives the LLM a student request and factual AY2026/27 course records. The LLM produces the final
eligibility decision, semester plan, refusal or missing-information response itself. Generation never calls a
solver or receives checker feedback. Answer checking happens afterward.

## Run with NUS SoCLaaS

Keep the key in SOCLAAS_API_KEY; never put it in source, a saved command or a result file.

```bash
python -m pipelines.run_a --provider soclaas --model x-test-2 --workers 8
```

For a pilot, add --ids q1-eligible-01 q2-loose-02 q2-tight-01 missing_info-q2-01. Then run the same command
without --ids to finish the remaining cases. Keep all other settings identical.

The client first fetches GET https://soclaas-api.comp.nus.edu.sg/v1/models, validates the exact chat model ID,
and saves discovery metadata. The current default, x-test-2, was listed as Test DeepSeek V4.1 Flash 1017.
The historical pilot supports a practical choice under its tested settings, not a general model ranking.
SOCLAAS_MODEL or --model overrides the preference.

Calls use /v1/chat/completions, stream: false, temperature 0, and a fresh system/user conversation per instance.
The client reads choices[0].message.content; the endpoint does not run programs. HTTP 429, temporary 5xx and
connection failures get at most four retries with waits of 2, 4, 8 and 16 seconds. Permanent HTTP errors are not
retried. The request timeout defaults to 600 seconds and is configurable with --timeout.

## Output format and budget

The v2 prompt requires one top-level JSON object with status and nonempty reasons. It explicitly forbids
eligibility, answer, result or nested plan wrappers. Only PLAN includes a plan mapping semester strings directly
to course-code lists. Eligibility decisions include five named boolean eligibility_checks; MISSING_INFO includes
missing_fields. These are claims generated by the LLM, not precomputed answers supplied in the prompt.

SoCLaaS defaults to an initial 16,384 completion tokens, including reasoning. If the provider reports truncation,
or the completion reaches its cap without usable final text, the client makes ONE fresh attempt at 32,768 tokens,
with exactly the same original messages. There is no continuation or grading feedback. It never retries merely
because an answer is wrong, malformed or suboptimal.

Every attempt retains raw final text, parsed answer, finish reason, usage, timing and exhaustion flag. Top-level
usage sums all budget attempts, including exhausted ones. A failure at the final cap remains a failure.

```bash
python -m pipelines.run_a --provider soclaas --workers 8 --max-tokens 16384 --retry-max-tokens 32768
```

Set --retry-max-tokens 0 for a fixed-budget condition. A nonzero retry cap must exceed the initial cap.
Changing the prompt or budget creates a different condition; do not combine it with old replies.

## Results and safe resumption

The default directory for these settings is results/A/x-test-2/route-a-v2_16384_32768/.
The old 8,192-token results remain in results/A/x-test-2/ and are not overwritten or reused by v2.
Use --out PATH for another condition directory. A manifest records model, prompt/catalogue/instance hashes,
budget, timeout and concurrency. Resumption refuses mismatched settings or legacy directories without a manifest.
Saved bad answers and error records remain outcomes; resumption skips them rather than sampling again.

Record selection follows prompt_a.py: benchmark request metadata selects named courses and their prerequisite
and corequisite closure. This tests direct reasoning with supplied course facts. The gold spec selects context
only and is not shown; the gold answer is never shown during real generation. This protocol does not claim to
evaluate automatic retrieval from a bare natural-language question.

## Check answer quality

```bash
python -m eval.grade results/A/x-test-2/route-a-v2_16384_32768
python -m eval.quality results/A/x-test-2/route-a-v2_16384_32768
```

SUMMARY.md and graded.csv report decision accuracy, plan violations and reference optimality.
QUALITY.md and quality.json additionally report:

- Output-contract compliance, without silently unwrapping answers.
- Independent verification of all five eligibility claims from the catalogue.
- Prerequisites, corequisites, offerings, preclusions (including reciprocal exclusions against completed courses),
  repeats, requested courses, semester limits, credits, hard wishes and unnecessary added courses in plans.
- Objectives, added-course counts and soft preferences compared with the saved reference plan.
- Whether missing_fields identifies information actually absent from the request.
- Independent simple conflict certificates for NO_PLAN: preclusions, capacity bounds, offering conflicts,
  missing strict prerequisites at the starting/final semester, ordering cycles and overfull fixed semesters.
- Unverified grade clauses that the completion-only transcript model cannot certify.
- Exhausted budgets, retries and retained API failures.

explanation_review.csv contains requests, actual responses and offline references for prose review. The audit
appends new cases and preserves notes for unchanged answers. Use assistant_pass, assistant_issue or pending to
distinguish assisted explanation review from mechanical checks. Use assistant_note for optional wording observations
that are not errors. A matching status does not prove every sentence
is true; a correct NO_PLAN label does not establish that its written conflict is valid. Running eval.quality again
incorporates review statuses and notes into quality.json.

Relative preferences are conservatively graded when the gold plan missed a wish and therefore does not establish
its optimal bound. Independently valid offline plans in preference_witnesses.json can disprove a relative optimum.
Such witnesses are review evidence only and never feed into model generation.

The independent checker never imports the catalogue resolver or solver. Review evidence and quality issues are
never fed back into generation, and original model responses are never repaired in place.

## Other compatible APIs and offline checks

Use --provider compatible with LLM_BASE_URL, LLM_API_KEY and LLM_MODEL in the environment. Its default cap is
4,000 with no escalation; configure explicit caps for comparable experiments. --mock gold tests the harness
without network access; reference objects are not evidence of LLM format compliance.

```bash
python -m ruff check .
python -m pytest -q
```

The previous four-model pilot is documented in results/model_selection/SUMMARY.md. Regrade saved responses
without new calls using:

```bash
python -m experiments.compare_route_a_models --instances results/model_selection/instances.json --report-only
```

That historical pilot used the old prompt, eight cases and an 8,192-token cap.
